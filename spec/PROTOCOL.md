# NHO/Arduino/1 — the New Horizons OS platform contract

This directory is the specification of what a device running New Horizons OS
exposes to the world. The firmware in `firmware/newhorizons_os/` is the
reference implementation; the Gateway, the Hub and the Desktop are clients of
this contract and test themselves against it.

| File | What | Written by |
|---|---|---|
| `PROTOCOL.md` | this overview: transports, envelopes, packet layout, apps, updates, compatibility | hand |
| `wire.json` | every wire constant (ports, magic, flags, sizes, time exchange) | hand; the only copy |
| `commands.md` | every control command, with its flags | generated from `ControlCommandTable.cpp` |
| `config.md` | every configuration key | generated from `ConfigRegistry.cpp` |
| `fixtures/versions.json` | version ordering vectors | hand |
| `fixtures/packets.json` | encoded v5 packets | generated by `tests_native` |

Generated files carry a `GENERATED` header. Regenerate with
`firmware/scripts/gen_wire.py` and `firmware/scripts/gen_spec_docs.py`; CI runs
both with `--check`. The app contract (`AppContract.h`) is generated from the
App Library's `sdk/lib/opset.mjs` (`nhos.mjs gen-contract`).

## 1. Transports

A device reaches the system one of two ways, chosen at boot (`set_transport`):

- **WiFi** — the device streams sensor packets over UDP to a Gateway found
  with FindMe, and takes commands from it.
- **Direct (ESP-NOW)** — the device pairs with a Hub (HELLO / PAIRED / POLL)
  and exchanges the same packets and commands over ESP-NOW.

Ports (`wire.json` → `ports`):

| Port | Use |
|---|---|
| 13250/udp | sensor packets device → Gateway; control commands and replies both ways |
| 22345/tcp | control, one JSON request per connection (local tools) |
| 22346/udp | FindMe: device discovery of Gateways |

## 2. Control commands

### Request

Over UDP a command is a JSON datagram:

```json
{"type":"command","seq":7,"request_id":"r-7","payload":{"command":"status","quiet":true}}
```

`payload.command` names a row of `commands.md`; the other payload keys are the
command's arguments. `"quiet":true` suppresses the command LED (a poller should
always set it). Over TCP the payload object alone is sent, newline-terminated.
Over ESP-NOW the Hub relays the payload object.

### Ack and reply

Over UDP the device answers in two steps:

1. at once, `{"type":"ack","device_uid":"…","ack":<seq>,"request_id":"…"}` — the
   Gateway stops retrying;
2. when the command has run, the result.

A result up to 1200 bytes is one datagram:
`{"type":"result","device_uid":"…","request_id":"…","payload":<reply>}`.
A larger one is split into `result_chunk` datagrams of 700 reply bytes each,
`{"type":"result_chunk",…,"chunk":i,"chunks":n,"data":"<slice>"}`, sent one per
gap between scans; the receiver joins the slices in order and parses the
whole as `<reply>`. Receivers reassemble by `request_id` with a 10 s TTL.

Over ESP-NOW a reply larger than one frame (7680 B) is paged: page 0 is the
reply to the command, and the Hub pulls the rest with
`{"command":"result_page","rid":R,"chunk":I}`.

Every reply has the same shape:

```json
{"ok":true,"cmd":"status","message":"status","data":{…},"error":""}
{"ok":false,"cmd":"file_delete","message":"maintenance_required","data":{},"error":"maintenance_required"}
```

Errors every command may return: `unknown_command`, `maintenance_required`
(a command flagged *maintenance* in `commands.md`, outside maintenance mode).

### Heavy commands

Commands flagged *heavy* (`status`, `query`, `storage_status`, `commands`) take
several milliseconds to build. Over UDP the device acks them at once and runs
them in the next gap between scans (at most ~40 ms later), so they do not delay
sampling. The reply is unchanged.

### Discovering the command set

`commands` (v1.15.0+) returns the dispatch table itself:
`{"hash":…,"count":…,"commands":[{"name","maintenance","heavy","quiet","internal","status_snapshot","summary"}]}`.
`capabilities` carries `command_schema_hash` and `command_count`, so a client can
tell when its cached copy is stale. Clients should prefer this table to a
built-in list: a command added to the firmware is then usable without a client
release.

## 3. Sensor packets (v5)

Little-endian throughout. Header, 24 bytes:

| Offset | Size | Field |
|---|---|---|
| 0 | 2 | magic `0xA55A` |
| 2 | 1 | version `5` |
| 3 | 1 | flags (below) |
| 4 | 6 | device UID (the WiFi STA MAC) |
| 10 | 4 | frame sequence |
| 14 | 8 | epoch milliseconds at scan time (valid only with `epoch_valid`) |
| 22 | 2 | payload length |

Payload, in this order, each block present only when its flag is set:

1. matrix levels: one float per sensor, row-major;
2. `raw_adc`: one float per sensor, the unprocessed reading;
3. `imu`: 7 floats (ax, ay, az in g; gx, gy, gz in deg/s; the 7th reserved, 0);
4. `mag`: 3 floats (mx, my, mz in µT);
5. `battery`: status u8, fault u8, vbat mV u16, state of charge in 1/100 % u16;
6. `extensions`: TLVs (type u8, length u8, value), at most 128 bytes in all;
7. `hmac`: reserved. The flag and its 16-byte size are allocated, but no
   producer sets it and no receiver checks it yet.

A `heartbeat` packet has the heartbeat flag and an empty payload. The sensor
count is not in the header: a receiver knows it from the device's
`matrix_shape`, or infers it from the payload length. Versions 2–4 are frozen
history, still accepted by the parsers.

## 4. Time

The device keeps one wall clock (`clock_status`). Its source follows the
transport: in WiFi mode a TIME_REQ / TIME_RESP exchange with the Gateway over
UDP, falling back to NTP; in Direct mode the same exchange with the Hub over
ESP-NOW; `set_time` as a last resort. The exchange is NTP-style (four
timestamps), so the radio round trip is measured, not added. Layout and magics:
`wire.json` → `time`. Corrections are slewed: packet timestamps never go
backwards.

## 5. Apps

An app is a package (`.nha`): a JSON document with `"nhapp":1`, a `kind`
(`flow` — a dataflow graph the device runs every frame — or `readout`, a view
the Desktop renders from polled commands), a `manifest` (id, version, `min_os`,
`capabilities`) and, for a flow, its `nodes`.

- **Ops.** The ops, their inputs, costs and the capability each needs are
  defined in the App Library's `sdk/lib/opset.mjs` and generated into the
  firmware's `AppContract.h`. The device checks a graph's worst-case cost
  against its budget at install, and refuses an over-budget graph.
- **Capabilities** are permissions and subscriptions in one bit: an app that
  may not read the matrix is not woken by frames. A package declares what it
  needs; the device never widens it.
- **`min_os`** is compared on the version core, so a beta can install an app
  that needs its release.
- Packages are installed with `file_write_*` + `app_install` (with `sha256`),
  activated per slot with `app_activate`, and observed with `app_list`,
  `app_view` and `app_events`.

## 6. /proc

`file_list` / `file_read_begin` / `file_read_chunk` with `"scope":"proc"` read
synthetic, read-only files: `version`, `uptime`, `tasks`, `services`, `apps`,
`packages`, `mem`, `scan`, `net`, `power`, `crash`, `health`, `kmsg` and
`crash.elf` (the last core dump). Writing to that scope fails with
`read_only_scope`.

## 7. Updates

Each board follows a channel (`ota.channel`): `stable` reads
`releases/arduino-<board>-latest.json`, `beta` reads `…-beta.json`. A manifest
names the version, the firmware URL, its size and sha256, and the board model.
Versions follow `vX.Y.Z` with prereleases `vX.Y.Z-beta.N`, ordered as in
`fixtures/versions.json` (a prerelease sorts below its release). Leaving beta
never downgrades: the device waits until stable passes its version.
`*-latest.json` never holds a prerelease (firmware before channels reads only
that file). Downloads verify the server's TLS certificate.

## 8. Compatibility rules

- Wire formats only grow. A new packet field is a new flag or TLV; a new reply
  field is a new key. Old receivers ignore what they do not know.
- A command's name, arguments and reply keys do not change meaning. A
  replacement is a new command; the old one stays until no supported client
  sends it.
- Clients check for features, not versions, where they can: `commands`,
  `capabilities.features`, `config_schema`.
- The flow-op numbering is append-only (the device persists op numbers with
  counter values).
- The OTA manifest `model` keeps the pre-rename board name (`VD-CTL/R …`):
  firmware before v1.8.1 accepts only an exact match.
