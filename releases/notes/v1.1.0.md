# v1.1.0

可安裝應用。v1.0.0 的 App 是編譯進韌體的靜態物件;本版把它變成真正的內容 ——
裝置上有套件註冊表、四個執行槽,以及一個從商店安裝的散佈路徑。

同時把執行引擎從 **Rule 改名為 Flow**,**不保留舊名稱與舊路徑**。

## 為什麼不叫 Rule 了

「Rule engine」在業界有明確意涵(Rete、Drools 那類):對事實做模式比對、有衝突
解消、有推論。這個引擎一樣都沒有。它是一張固定順序的節點圖,每次事件從頭算到尾
—— 學理上就是**同步資料流**。舊名字讓人預期一套不存在的機制。

對應的改名(全面替換,無別名):

| v1.0.0 | v1.1.0 |
|---|---|
| `RuleEngineApp` / `RuleOp` / `RuleNode` | `FlowApp` / `FlowOp` / `FlowNode` |
| `app_load_rules` / `app_unload_rules` | `app_load_flow` / `app_unload_flow` |
| `apps/rules.json` | `apps/flow.json` |
| `rule_load_failed:` / `rule_engine_unavailable` | `flow_load_failed:` / `flow_engine_unavailable` |
| 槽名 `rules` | 槽名 `flow` / `flow1` / `flow2` / `flow3` |

## App 不再是掃描的乘客

v1.0.0 的 `apps.onFrame()` 寫在 `scanAndStreamIfDue()` 裡,而它自己只是排程器的
一個任務。後果是:App 的頻率恆等於掃描頻率、掃描停止時 App 全部靜止、而且只看得
到矩陣與 IMU —— 按鍵、電池、連線、時間都無法觸發它。「每幀預算」之所以存在,
也只是因為幀是當時唯一的時鐘。

現在 App 是排程器裡自己的一項 (`apps`),介面改為事件式:

```cpp
enum class AppEventKind { Frame, Imu, Tick, Button, Power, Link, Budget, Custom };
class App { virtual void onEvent(const AppEvent&) = 0; };
```

**訂閱與權限是同一個 bit**。沒有 `read_matrix` 的 App 收不到 Frame —— 兩份可能
互相矛盾的清單,不如一份。只訂閱 `Tick` 的 App 在掃描停止時照常運作;只訂閱
`Frame` 的 App 在掃描停止時完全不耗成本。

`apps` 任務**註冊在 `scan_stream` 之後**,所以它拿到的是剛掃出來的那一幀,而且是
掃描器自己的資料,沒有多一次複製。這個順序是正確性的前提,不是風格 —— 寫反了會
讓 App 拿到上一幀,而且沒有任何錯誤徵兆。

## 掃描永不降級

App 的時間額度**不是設定值,是剩餘量**。`AppGovernor` 觀察掃描是否趕得上截止
期限,並據此增減 App 可花的總量,必要時減到零(全部暫停)。裝置存在的理由是取樣
矩陣,App 是額外價值,不能以它為代價。

- 權威訊號是 `ScanHealth::overrunFrames`,**不是 `Scheduler::busyPermille()`。**
  後者在任何執行掃描的 tick 上都合理地偏高 —— 排程器自己的註解記錄過這個教訓:
  舊版拿它當判準,在真實硬體上 4085 次裡誤報了 4083 次。
- AIMD:讓路用乘性下降,收復用加性回升(五個乾淨的觀察窗才收回一個壞窗的代價)。
  不對稱是刻意的,否則迴路會震盪、使用者看到 App 一直在暫停與恢復之間跳動。
- 暫停後至少維持 5 秒,避免邊緣 App 直接恢復到同一個過載裡。

**新增 `AppState::Suspended`,與 `Killed` 嚴格區分:**

- `Killed` = App 自己的錯(連續超出自己的額度),需要 `app_revive` 明確認可。
- `Suspended` = 系統壓力所致,**壓力解除自動恢復**。

混為一談的後果很糟:一個不會自動恢復的暫停,等於裝置忙過一次之後 App 就再也沒
回來,而使用者不會知道為什麼。

## App 會被告知,然後才被停用

超額時警告**同時送兩邊**:送給操作者(走 `app_events`,因為使用者有 App 沒有的
手段 —— 停用別的 App、改圖、調高上限),也送給 App 自己(`Budget` 事件,帶
`load` 與 `grace_left`)。App 可以據此少做一點,也可以什麼都不做等著被停用 ——
那是它的選擇,不是系統替它決定的。

自我降級必須留痕:`gate` 一生效就發 `degraded` 事件。理由很實際 —— 這是研究資料
收集裝置,一個訊號因為「剛好多開了兩個 App」而悄悄改變保真度,會在資料裡留下一個
與受試者無關的階躍。記錄下來它就只是誠實。

## Flow VM:算術、時序與條件

v1.0.0 的七個 op 只能表達「區域閾值事件」。做不到比值、差值、滑動窗、積分 ——
也就是說壓力中心的左右偏移、步頻、衝量這些最常用的生物力學量,一個都寫不出來。

新增:

```
算術  const add sub mul div min max abs clamp
時序  mean(n) max_hold(n) delta integrate(n) counter    ← 宣告期固定長度的環形緩衝
掃描  features feature_get arg_max row_centroid col_centroid
輸出  led emit_value
條件  select gate budget_load grace_left
```

**保留的約束:無迴圈、無動態配置、節點只能引用更早的節點。** 於是執行時間恆有
上界(最壞情況 = 每個節點都跑),成本依然能在載入時估出來。

條件**不**破壞這個上界 —— 破壞它的是迴圈,而這裡沒有。`gate` 一律以最壞情況
計價(當作它從不跳過):取平均會低估,讓安裝時的估算在最需要準確的那些幀上騙人。
`gate` 跳過的是**後續**節點而非先前節點,因為資料只能後向引用,一個子樹在 gate
執行到時早已算完。

## 原生 App 層取消

v1.0.0 有兩個 App 子類:`features` 與 `rules`(後者本身是引擎)。也就是說原生層
實際上只有 `features` 一個 —— 而且查證後確認**沒有任何程式碼消費它**,ESP-NOW
傳輸沒用到,測試也零引用。它是一個沒人讀的遙測 App。

所以:`FeatureExtractorApp` 刪除,單趟迴圈搬進 `features` intrinsic op。
**效能不足時的出口是「加 intrinsic」,不是「寫原生 App」** —— intrinsic 被成本
模型涵蓋且可被任何圖組合,原生 App 對估算器是不透明黑盒。

`features` 改為商店上架的一般 App。它能用 11 個節點完整表達(編譯器把 8 次
`feature()` 讀取收斂到同一趟掃描),這同時是 op 集合是否夠用的驗收標準。

> **升級注意**:`app_list` 不再含 `features`。NVS 的 `app_en_features` 成為孤兒
> 鍵(無害)。要保留這個功能請從商店安裝 `features`。

## 套件與註冊表

`.nha` = 單一 JSON,含 manifest 與 flow 圖。`nodes` 與 `name` 放**頂層**,所以
`FlowApp::parse()` 原封不動吃整包 body。

`apps/index.json` 記錄已安裝套件與槽位綁定。**索引寫入不是原子的** ——
`Storage::writeTextFileAtomic()` 在 SPIFFS 上是 remove 後 rename,中間有斷電
窗口。對策不是假裝有交易保證,而是把索引當**衍生資料**:

- index 壞掉但 `index.json.tmp` 可解析 → 採用 tmp 並立刻重存。
- 兩者都沒有但 `apps/` 下有 `.nha` → 自動 `app_reindex` 重建(manifest 內嵌在
  套件裡正是為此)。唯一真正遺失的是槽位綁定。

變動順序刻意選成失敗皆可回復:**uninstall 先寫索引再刪檔**(崩潰只留孤兒檔,可
reindex;反之會留指向已刪檔的索引項,那才無解)。install 會對暫存引擎**乾跑**
整張圖,壞套件在安裝時就被拒,而不是等到啟用才爆。

## 事件終於送得出裝置

v1.0.0 的 `emitEvent` 只寫進一個 **8 格**的 RAM 環形緩衝就結束 —— 沒寫檔、沒進
`NHO/Arduino/1`、沒推播。步態偵測每秒約兩個事件,**四秒就轉完一圈**,而且事件
無法與感測資料對齊。`kAppCapDriveLed` 有定義但 `AppHost` 根本沒有對應方法。

本版:

- 環形緩衝 8 → **32**(約 16 秒餘裕,對次秒級輪詢綽綽有餘;64 會為沒人用的餘裕
  多付 6.8KB 靜態 RAM)。
- 每筆事件帶**全域序號**與 **`frame_seq`**,後者直接取 `MatrixFrame::seq` ——
  這是事件能與錄製 CSV 對齊的關鍵。
- `app_events {since_seq}` 拉取,並回報 `dropped`:**遺失的事件與從未發生的事件
  不可以看起來一樣**。
- `AppHost::setLed()` 與 `emitValue()` 補上,讓宣告過的權限位真的可用。

**不動 `NHO/Arduino/1`,Gateway 與 Hub 零修改。**

## 上傳完整性

`file_write_finish` 新增可選 `sha256`。`file_write_chunk` 只驗證 offset 連續,
所以長度正確但內容損壞的 chunk 目前會靜默通過。不符時韌體**刪除該檔**:一個看起來
完整的損壞檔比沒有檔更糟,因為下一步會照用不誤。

## 記憶體

靜態 RAM +12.7KB(127480 → 140160,42%),flash +40KB(44%)。主要來自四個
`FlowApp` 實例(各含 12 節點與 128 float 的環形緩衝池)、註冊表 8 筆、事件環形
緩衝,以及交接用的一份 `MatrixFrame`。

## 相容性

- **破壞性**:`features` 消失、`app_load_rules` / `app_unload_rules` 消失、
  `apps/rules.json` 不再自動載入。舊 Desktop 送舊指令會收到 `unknown_command`。
  請搭配 Desktop v0.9.0 以上。
- 線上格式 `NHO/Arduino/1` 未變,Gateway / Hub 不需要任何修改。
- `app_list` / `app_enable` / `app_disable` / `app_revive` 語意不變。
