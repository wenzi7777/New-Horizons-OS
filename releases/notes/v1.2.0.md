# v1.2.0

新增第二種套件類型：**readout**。

## 為什麼

v1.1.0 的套件只有一種：`flow`，在裝置上每幀執行的資料流圖。但「任務管理器」這類
東西根本不該在裝置上執行 —— 它只是把裝置已經量到的數字讀出來。資料流圖也渲染不出
UI，它沒有任何 UI 原語。

所以 readout 是**宣告式的介面描述**：它列出要輪詢哪些裝置指令、要畫哪些元件。
韌體**完全不解讀它的內容**，只負責存下來與回報；渲染由 Desktop 做。

## 為什麼仍然裝在裝置上

最直覺的作法是把它裝進 Desktop 就好 —— 但那樣「這台裝置裝了什麼」就只存在於當初
安裝它的那台電腦裡。換一台電腦連上同一個裝置，就看不到了。

**裝置才是「它裝了什麼」的事實來源**，所以 readout 照樣進 registry、照樣出現在
`app_list_packages`、照樣跟著裝置走。它只佔一個 registry 項目：

- **沒有槽位**：`app_activate` 對它回 `not_activatable:readout`。綁到槽上會讓那個
  槽看起來被佔用卻什麼都不派送，誤導任何讀 roster 的人。
- **沒有預算、不被派送**：它不進 `AppManager`，不耗任何幀時間。
- **沒有任何權限**：它在裝置上不執行，所以 capabilities 是空的。

## 安全性：宣告式，因此不帶程式碼

這點比裝置端更重要 —— readout 是在**操作者的瀏覽器裡**渲染的。

它只能列出指令與元件，帶不了程式碼，所以安裝一個 readout 不會執行任何東西。可輪詢
的指令是白名單，**全部唯讀**：`task_list`、`service_list`、`app_list`、
`app_events`、`memory_status`、`scan_health`、`storage_status`、`status`、
`capabilities`。任何寫入類指令都會被拒（`readout_source_not_allowed`）。

這道白名單在三個地方各驗一次：App Library 的 CI、Desktop 後端、以及瀏覽器端的
渲染器 —— 因為套件可能來自被手改的目錄。

## 韌體改了什麼

很少：

- `AppPackage::parseManifest` 接受 `kind: "readout"`，並給它零權限。
- `AppRegistry::install` 對 readout 跳過圖的乾跑（它沒有圖）。
- `AppRegistry::activate` 拒絕 readout。
- `restore()` 不會嘗試把 readout 綁到槽。
- 索引持久化 `kind` —— 少了這個，readout 重開機後會變回 flow，裝置就會試著執行它。

## 首個 readout：System Monitor

`sysmon`（3237 B）顯示排程器負載、掃描速率與錯過的截止期限、記憶體（含
**最大連續可用區塊** —— 碎片化指標，先前沒有任何地方看得到）、以及任務 / App /
服務三張表。

**只顯示真實可量測的東西。** 裝置沒有每任務的 RAM 歸屬，也沒有電流感測器，所以
這裡**刻意沒有**每任務 RAM 與電力欄位 —— 一個看起來像 macOS 但其實是編出來的
數字，比沒有那一欄更糟。

實機上它立刻顯示出兩件先前看不到的事：`imu` 任務佔 24.6% CPU、每次 5.08ms；
以及 heap 空閒 131.1 KB 但最大連續區塊只有 48.0 KB。

## 相容性

- v1.1.0 的裝置會以 `unsupported_kind:readout` 拒絕 readout 套件 —— 這正是 `kind`
  欄位存在的用意。`sysmon` 的 `min_os` 因此是 `v1.2.0`。
- flow 套件、指令、線上格式全部不變。Gateway / Hub 不需任何修改。
