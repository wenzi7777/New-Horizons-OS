# v1.7.0

**App 驅動的狀態 LED 真的看得到了**，而且多個 app 同時使用 LED、OLED、燈條時，由誰勝出有明確規則。
新的唯讀指令 `app_view` 會回報這些輸出目前實際顯示的內容，讓 Desktop 可以即時鏡像。

## 為什麼

`led` op 以前直接寫狀態 LED 的像素，系統的 LED 任務每 10 ms 會重畫一次系統燈號，所以 app 的顏色
大多只亮一瞬間。兩個 app 同時寫時是後寫的贏，也沒有任何 slot 仲裁。此外，app 在 OLED 和燈條上畫了什麼
完全不會回報：沒有 OLED 的 GCU 板上看不到，OLED 不在 app 頁時也看不到。

## 變更

- **狀態 LED 分層仲裁**：
  - app 的顏色改由 AppManager 在每次 LED 更新時拉取，由編號最小、正在執行、持有顏色的 slot 勝出，
    跟 OLED 行和燈條的規則一致。slot 停止、被停用、被 kill 或暫停時會自動釋放。
  - `led` 的觸發條件上升時持有顏色，**下降時把 LED 交還給系統**（以前是寫成全黑）。
  - app 的顏色只會取代「正常上線」的基本燈號：Online，以及單顆燈板子插電時代替它的充電、充飽燈號。
    開機、錯誤、記憶體不足、OTA、Wi-Fi/Hub 斷線、FindMe、維護與安全模式、掃描警告、軟關機，
    以及指令確認閃爍，都一律由系統優先，結束後 app 的顏色自動恢復。
- **新唯讀指令 `app_view`**（不需要維護模式，`capabilities.subsystems.app_view` 為 true）：
  - `oled`：4 行 app 內容（用上屏同一組函式格式化），每行由哪個 slot 畫、有哪些 slot 同時在搶，
    以及面板目前的頁面、是否正在顯示 app 頁、板子有沒有 OLED。沒有 OLED 的板子也會回報。
  - `status_led`：像素目前的邏輯顏色、背後的系統訊號、擁有者（`system` 或 slot 名稱），
    以及 app 的請求是否被系統壓下、是否有其他 slot 在搶。
  - `ext_led`：燈條由誰驅動；由 app 驅動時附上每個像素的顏色。
  - 回應約 1 KB 以內，在 ESP-NOW 回應上限內。

## 驗證

- 5 塊板子的 release build 均通過；`tests/` 靜態測試（新增 5 個仲裁檢查）、App Library SDK 測試全部通過。
- 程式大小相對 v1.6.0 約 +4.3 KB。
- **本版尚未經過實機驗證**：LED app 觸發後是否維持顏色、系統狀態是否正確蓋過 app、多 app 衝突回報，
  以及 Hub 模式下的 `app_view`，都需要在實機上確認。

## 相容性

- 依賴舊行為的 app：`led` 下降沿以前會把 LED 寫成全黑，現在會回到系統燈號。
- 模擬器不知道系統狀態，所以永遠顯示 app 的顏色。
- Desktop v0.14.0 起，裝置設定的 App 頁籤會用 `app_view` 顯示即時的虛擬 OLED、狀態 LED 與燈條。
