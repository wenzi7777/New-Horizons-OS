# v0.16.1

## Fix: Gateway path commands never reached the device (empty status / delivery timeout)

Since v0.12.0's `UdpStreamTransport` extraction, wifi_udp mode bound **two**
`WiFiUDP` sockets to port `13250`:

- a leftover global `streamUdp` (polled by `serviceUdpCommand`)
- `udpTransport`'s own socket (used for outbound stream frames)

On ESP32/lwIP the second bind steals inbound packets. Outbound streaming still
looked healthy (Gateway `last_seen` kept updating), but control commands never
arrived (`control_command_received` never logged → Gateway
`command_delivery_timeout` → Desktop `last_status` never got real
`firmware_version` / nested status objects). Hub/ESP-NOW devices were
unaffected.

### Changes

- Single `WiFiUDP` for the whole wifi_udp path: only `udpTransport.begin()`.
- `serviceUdpCommand(udpTransport.udp())` polls that same socket.
- Heartbeat now sends via `activeTransport->sendFrame()` instead of the
  removed global socket.
- Scaffold regression test locks the single-socket pattern in place.

## Also in this release

- Holding the boot Action Button now wins over a persisted ESP-NOW/Hub
  transport mode, so a device that has paired with a Hub can still re-enter
  the WiFi setup portal.
- Saving credentials in the WiFi portal persists `transport=wifi_udp`, so the
  next reboot stays on the Gateway path instead of snapping back to ESP-NOW.

## Companion host fixes (separate repos)

- **New-Horizons-Desktop v0.5.7**: do not treat `command_delivery_timeout` /
  other transport errors as status snapshots (avoids clobbering `last_status`).
- **New-Horizons-Gateway v0.5.5**: import `__version__` so direct runtime start
  works when `NEWHORIZONS_GATEWAY_EXPECTED_VERSION` is unset.
