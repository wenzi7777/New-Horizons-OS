# v0.15.1

## Changes

### Hardening: check `esp_now_send()`'s return value when sending a control-command response

Continued real-hardware debugging of `command_delivery_timeout` (still occurring for some devices after v0.15.0) found `EspNowPairing::serviceCommand()`'s response-fragment pacing loop never checked `esp_now_send()`'s return value -- a failed send (e.g. `ESP_ERR_ESPNOW_NO_MEM` from a busy internal TX queue) would silently drop that one fragment while the send loop still advanced past it, permanently losing the whole response even though every other fragment went out fine. The loop now only advances on a successful send; a failed one retries the same fragment on the next paced tick.

### Diagnostics: register an ESP-NOW send-status callback

Added `esp_now_register_send_cb()` (previously never used anywhere in this codebase) so a genuine over-the-air send failure -- distinct from `esp_now_send()`'s own synchronous return, which only confirms a packet was accepted into the driver's queue, not that it was actually transmitted -- is now logged (`[espnow] send_cb_fail`). This is diagnostic-only (logs failures only, silent otherwise) but gives real visibility into a failure mode this project had no way to observe before.

## Known issue, not resolved by this release

Real-hardware testing this round reproduced `command_delivery_timeout` even for an isolated `status` command with no other command in flight, in a way that did **not** correlate cleanly with any single cause identified in code -- ESP-NOW airtime contention (already addressed in v0.15.0/v0.14.0), the Hub's own uplink relay and poll cycle (investigated this round, ruled out as the primary cause), and this release's `esp_now_send()` hardening were all checked and did not fully eliminate the failure. The new send-status callback confirms the device's own sends report success (both synchronously and via the driver's async callback) even when the Hub never receives them, and testing showed the failure rate varying across the session in a way that's consistent with real-world WiFi/RF conditions rather than a specific, fully-isolated software bug. Two more invasive fixes (pausing the Hub's own ESP-NOW poll cycle during a pending command, and aborting an in-flight sensor-data fragment burst on the device when a command arrives) were built, tested, and **reverted** after they did not measurably improve reliability and could not be conclusively ruled out as net-neutral -- shipping only the hardening above, which is safe and verified not to regress anything.

If `command_delivery_timeout` continues to occur, the next diagnostic step is registering the equivalent send-status callback on the Hub side and testing in a quieter RF environment to separate software from environmental causes.

## Also in this release
