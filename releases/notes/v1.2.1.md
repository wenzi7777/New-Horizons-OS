# v1.2.1

IMU 讀取成本減半：每次讀取 **4.6 ms → 2.3 ms**，數值不變。

## 問題

v1.2.0 的 `sysmon` 第一次讓 `imu` 任務的成本看得見：每次呼叫 5.08 ms，佔 24.6% CPU。
而 BMI270 一次加速度 + 陀螺儀讀取在 I2C 上只是 12 個位元組。

原因有兩層：

1. `ImuManager::begin()` 呼叫了 `IMU.setContinuousMode()`，開啟 BMI270 的 FIFO，
   但 FIFO **從未被排空** —— 只有 `accelerationAvailable()` 會讀 FIFO，而韌體從不
   呼叫它。於是每次讀取都落回 library 的非 FIFO 路徑。
2. 在那條路徑上，`readAcceleration()` 與 `readGyroscope()` **各自**做一次完整的
   `bmi2_get_sensor_data()`，每次都讀回加速度 + 陀螺儀兩者。一個樣本付了兩次完整讀取
   的代價，其中一半直接丟掉。

## 修正

新增 `ImuDriver`：`BoschSensorClass` 的子類別，透過 library 預留的
`configure_sensor()` 覆寫取得 `bmi2_dev`，並提供 `readAccelGyro()` ——
**一次** `bmi2_get_sensor_data()` 同時取回兩者。移除無用的 continuous mode。

刻意**沒有**改成直接讀暫存器：`bmi2_get_sensor_data()` 會套用 BMI270 的出廠陀螺儀
交叉軸補償（`gyr.x -= zx * gyr.z / 512`）與軸向重映射，自己讀暫存器會悄悄丟掉它。
換算常數（±4 g → 8192 LSB/g、±2000 dps → 16.384 LSB/dps）與 library 相同。

BMM150 磁力計（v1.0.F）改走同一個 `imuDriver` 實例 —— 只有被 `begin()` 過的那個物件持有已初始化的 BMM150，所以不能再讀 library 的全域 `IMU`。

## 實機驗證（v1.5.F）

同一次開機內 A/B 交替讀取 200 個樣本：

| | 每次讀取 |
|---|---|
| 舊路徑 | 4568 µs |
| 新路徑 | 2272 µs |

數值差異：加速度平均絕對差約 0.0002 g；陀螺儀 0.0034–0.0055 dps，**小於 1 LSB
（0.061 dps）的十分之一**，含受交叉軸補償影響的 `gyr_x` —— 也就是補償確實保留了。

最終版本：讀取 2.5 ms，52 Hz，`imu` 任務 CPU 24.6% → 14.3%。

`imu_status` 新增 `sample` 欄位（`[acc_x, acc_y, acc_z, gyr_x, gyr_y, gyr_z]`），
讓最新一筆讀數可以直接比對。

## 相容性

無破壞性變更。線上格式、指令、App 套件格式皆不變。
