# v0.11.4

## Changes

### Fix: IMU disabled unintentionally by a short/glitchy action-button press

- The soft-off long-press threshold (`kLongPressMs`) was 1500ms with no debounce on
  the action-button GPIO read. A brief contact bounce or a floating pin reading a
  spurious LOW could register as a sustained press and trip full soft-off — which
  disables the IMU along with Wi-Fi and the scanner — well before the user intended.
- `PowerStateManager` now debounces the raw GPIO read (30ms stability required before
  a press counts) and raises the long-press threshold to 3000ms, so a real deliberate
  hold is still detected but transient noise no longer is.

### Fix: status LED stuck on gateway-pending after Wi-Fi connects

- `FindMeClient::hasGateway()` required `attachedThisBoot_`, which `begin()`
  unconditionally reset to `false` on every boot — even though the previously
  attached gateway's host/port/id were loaded from persistent storage right above it.
  This meant the LED could never reach `Online` (green) until a fresh `findme_offer`
  UDP packet happened to arrive after every single reboot, regardless of Wi-Fi state.
- `begin()` now trusts a persisted gateway attachment immediately if the stored
  host/port are usable, while still refreshing in the background (without clearing
  the attach flag) to confirm or update it.

### Diagnostics: IMU sampling rate stuck around 55Hz regardless of requested value

- Investigated a report that requesting 60Hz or 90Hz IMU sampling had no effect
  (measured rate stayed ~55Hz). The BMI270 sensor chip itself is already configured
  for 100Hz ODR in the vendored `Arduino_BMI270_BMM150` library, so the chip is not
  the bottleneck — the real cap is most likely `loop()`'s own achievable cycle time
  (from Wi-Fi/FindMe/ControlServer/display housekeeping each iteration), which limits
  how fast `ImuManager::service()` can actually be called regardless of the requested
  poll interval.
- This release does not yet change the sampling-rate behavior. It adds
  instrumentation instead: `ImuManager` now tracks a real measured samples/sec
  (`measured_rate_hz` in its status JSON) instead of only reporting the requested
  poll interval, and `loop()` reports a per-section timing breakdown
  (scan/wifi/findme/control/imu/led/display, average and max, over ~3s windows) via
  serial. Flashing this build and reading the `loop_profile ...` serial lines will
  show which section is actually consuming the time budget, which determines the
  right fix for the next release.
- Also confirmed disabling the matrix scanner does **not** help on its own:
  `imu.service()` already runs unconditionally every `loop()` iteration regardless of
  scanner state, and the IMU's poll interval is currently only ever set indirectly via
  the scanner's `target_fps` (`set_scan_timing`) — a real fix will need to give the
  IMU its own independent rate-setting path, not just toggling the scanner.

## Verification

- ESP32-S3 Arduino compile for all four board models:
  - `VD-CTL/R v1.0.F 2026.4`
  - `VD-CTL/R v2.3.D GCU LTS`
  - `VD-CTL/R v2.2.C GCU LTS`
  - `VD-CTL/R v2.1 GCU LTS`
- Root Python test suite (`python3 -m unittest discover -s tests -q`) passes except
  two pre-existing failures unrelated to this change (stale `kPacketVersion`/
  `buildMatrixPacketHeader` signature expectations in test fixtures).
- **Not flash-tested on real hardware** — this has only been build-verified. The
  button-debounce and gateway-attach fixes should be confirmed on a real device;
  serial `power_transition_requested`/`loop_profile` output should be reviewed once
  flashed.
