# v0.14.0

## Changes

### Fix: New Horizons Direct (ESP-NOW/Hub) devices could get stuck with an ambiguous LED and no way back to WiFi setup

- The onboard LED had no awareness of ESP-NOW pairing state -- a device in
  Direct/Hub mode showed the same orange-breathing "connecting" signal the
  entire time, whether it was still discovering a Hub, mid-pairing, or had
  been successfully paired and streaming for hours. It's now a distinct
  `EspNowConnecting` signal that switches to solid green `Online` once the
  device is actually paired -- matches the transition a WiFi-mode device
  already gets once connected.
- A device with a *known* Hub MAC (paired before, now unreachable -- Hub
  off, moved, factory-reset) previously retried forever with no timeout at
  all. It now gives up after ~2 minutes and falls back to the WiFi setup
  portal on its next boot, same as the existing empty-MAC discovery case
  (which already had this). Fixed alongside two related gaps this exposed:
  the boot-time portal-fallback check no longer special-cases the
  empty-vs-known-MAC distinction (that would have caused a restart-every-2-minutes
  loop that never reached the portal once both cases could set the same
  failure flag), and `set_transport` now clears a stale failure flag on a
  deliberate reconfiguration so a freshly-paired device isn't bounced
  straight back to the portal because of unrelated leftover state.
- WiFi-mode devices had the same class of gap one level up: the one-shot
  boot-time connect attempt already fell back to the setup portal on
  failure, but the ongoing background reconnect (after a previously-working
  connection drops) retried silently forever with no fallback at all. It
  now also reopens the setup portal after ~2 minutes of failing to
  reconnect. Stored credentials aren't cleared either way -- the portal
  just becomes reachable again with the previous SSID pre-filled.

### Fix: ESP-NOW OTA relay now pauses this device's own sensor streaming

- Real-hardware testing found the device's own sensor-data uploads
  compete with an in-progress OTA relay for the same ESP-NOW airtime,
  making the relay far slower than expected whenever streaming continued
  unpaused alongside it (see New-Horizons-Hub's v0.2.0 notes for the
  relay feature itself). The device now pauses its own uploads for the
  duration of the actual chunk transfer and resumes normally once it
  finishes or aborts -- no special draining logic needed, since the
  sensor ring buffer already just drops the oldest queued frames while
  paused, the same lossy-by-design behavior it already has elsewhere.

## Also in this release

- Two related fixes on the New-Horizons-Hub side (device roster no longer
  falsely reports a migrated-away device as still connected forever, and
  the same `EspNowConnecting` LED signal added there too) ship together
  with this release -- see New-Horizons-Hub v0.3.0.
