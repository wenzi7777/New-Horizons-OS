# v0.11.2

## Changes

### Raise the matrix scan rate ceiling from 90 to 120 FPS

- `kMaxTargetFps` (`Config.h`) controls the upper bound accepted by
  `MatrixScanner::setTiming()` for `set_scan_timing`. It was `90`, a ceiling
  that predates the `delay(1)` → `yield()` scan-loop timing fix in v0.6.7 and
  was never revisited afterward — no part of the current timing model derives
  90 from actual scan cost.
- Requests above the ceiling are rejected outright (`scan_timing_invalid`),
  not clamped, so the device silently keeps its previous scan rate — this
  also means IMU sample rate (which mirrors scan rate) stays unchanged when a
  request is rejected, which is correct behavior but can look like nothing
  happened if you're not watching the operation log.
- The ceiling is now `120`. This is not a hardware measurement — the scan
  loop's actual per-column/per-cell timing budget (`settle_us * columns` vs.
  the frame interval) is still unvalidated in code at any FPS, so very high
  `settle_us` values on the largest matrix (`VD-CTL/R v2.3.D GCU LTS`, 15×15)
  could still overrun. Watch `scan_health.overrun_frames` /
  `max_scan_duration_us` after adopting higher scan rates.

## Verification

- ESP32-S3 Arduino compile for all four board models:
  - `VD-CTL/R v1.0.F 2026.4`
  - `VD-CTL/R v2.3.D GCU LTS`
  - `VD-CTL/R v2.2.C GCU LTS`
  - `VD-CTL/R v2.1 GCU LTS`
- Not flash-tested on real hardware at 120 FPS before release (skipped at the
  requester's discretion). Recommend checking `scan_health` telemetry after
  upgrading, especially on `VD-CTL/R v2.3.D GCU LTS`.
