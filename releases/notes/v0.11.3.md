# v0.11.3

## Changes

### Device sends a real wall-clock timestamp directly in every packet (protocol v4)

- The UDP packet's `timestamp_ms` field has always been `millis()` since boot, not a
  real date/time. This was invisible while nothing downstream used it, but the
  backend's CSV export was silently falling back to its own receipt-time wall clock —
  wrong for any sample buffered on-device (`MatrixScanner`'s stream-buffer queue) and
  sent late.
- The device now syncs its system clock over NTP (`configTime()` against
  `pool.ntp.org` / `time.google.com`) once WiFi is up (`TimeSync` module), and once
  synced, embeds the **real current epoch time directly** in every packet it sends —
  no reconstruction or side-channel needed.
- Real epoch milliseconds doesn't fit in the old 4-byte timestamp field (max ~4.29
  billion, ~49.7 days; real epoch ms today is ~1.7 trillion), so the field is widened
  to 8 bytes. This is a **protocol version bump (`NHO/Arduino/1` v3 → v4)** with a
  **header layout change** (20 → 24 bytes, `payload_len` shifts from offset 18 to 22).
  A new flag bit (`kPacketFlagEpochValid = 0x10`) marks whether the field holds a
  genuine synced timestamp; before NTP completes (or if the network has no path to
  NTP), the device sends `0` with the flag clear rather than blocking sensor
  streaming, and the backend falls back to its previous receipt-time behavior for
  those samples exactly as before this feature existed.
- v2/v3 packets (old firmware) still parse correctly wherever the parser is deployed —
  this is an additive protocol version, not a breaking cutover.

## Companion changes (required together)

Because this changes the wire header layout, three other components need matching
updates, all included in this same change set:

- **Desktop backend** (`New-Horizons-Desktop`): `packet_parser.py` and
  `arduino_protocol.py` now branch on packet version to pick the right header
  length/struct; `service.py`'s CSV writer prefers the device's real
  `device_epoch_ms` when present.
- **Gateway** (`New-Horizons-Gateway`): `arduino_protocol.py`'s packet classification
  (`is_arduino_stream_packet`/`is_arduino_heartbeat_packet`) also needed the same
  version-aware branching — the Gateway is not fully protocol-blind, it hardcodes the
  header version/length for its own routing/validation.

**Operational note:** the Gateway is a separately-run, host-only service that is not
OTA-updated. Anyone running a Gateway instance must pull and restart it with this
change *before or alongside* rolling out v4 firmware — an unupgraded Gateway will fail
to recognize v4 packets as valid Arduino stream packets until updated.

## Verification

- ESP32-S3 Arduino compile for all four board models:
  - `VD-CTL/R v1.0.F 2026.4`
  - `VD-CTL/R v2.3.D GCU LTS`
  - `VD-CTL/R v2.2.C GCU LTS`
  - `VD-CTL/R v2.1 GCU LTS`
- **Not flash-tested on real hardware** — this has only been build-verified.
  Recommend confirming on a real device that: (1) NTP sync completes on your WiFi
  network, (2) packets carry a plausible real epoch value once synced, and (3) the
  Desktop backend's CSV output reflects real epoch time before relying on it for data
  collection.
- Backend and Gateway packet-parsing/classification logic was smoke-tested standalone
  for v3 (legacy), v4-synced, v4-not-yet-synced, and truncated-packet cases — all
  parse/classify correctly and truncated packets raise/return cleanly rather than
  crashing.
