# v0.15.0

## Changes

### Fix: ESP-NOW control commands could fail entirely, and the device's LED blinked repeatedly for a single command

Real-hardware debugging (concurrent Hub+device serial capture while sending a
live `status` command) found the Hub's command dispatcher resending the raw
command every 500ms for up to 30 attempts (~15s) without ever accepting a
reply, even though the device answered correctly on every single attempt.
Two compounding causes, both fixed:

- The device's own sensor-data streaming was never paused during a
  control-command exchange, so it competed with the (up to ~11-fragment)
  command response for the same ESP-NOW airtime -- the same class of
  contention already found and fixed for the OTA relay
  (`EspNowOtaReceiver::isRelaying()`) and the stream transport's own send
  pacing. The device now pauses streaming for the duration of a pending
  command, from receipt through the full paced response send
  (`EspNowPairing::hasPendingCommandWork()`).
- The ESP-NOW control channel had no ack, unlike the UDP/Gateway path
  (which sends a tiny ack *before* executing so the Gateway's resender stops
  immediately). The device now sends a one-byte ack the instant a command
  frame finishes reassembling; the Hub stops resending the raw command as
  soon as it's acked and switches to a separate, longer deadline for the
  (possibly slow) response. This also removes the repeated-LED-blink
  symptom, since the device no longer reprocesses (and re-signals) the same
  command on every blind resend.

Verified on real hardware: a `status` command that previously failed with
`command_delivery_timeout` after 29+ resends now succeeds on the first
attempt, with no extra LED events.
