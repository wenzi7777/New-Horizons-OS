# v0.15.2

## Fixed: every `status` command over New Horizons Direct (ESP-NOW) failed with `command_delivery_timeout`

The Desktop app's device settings page showed nothing from a Hub-connected
device -- no matrix size, no firmware/hardware version, no Diagnostics.
Root-caused to **two independent bugs**, both now fixed. Verified on real
hardware: `status` went from failing every time to 8/8 successes, including
in the sustained-streaming state that previously never worked.

### 1. The response was too large for the wire format, and failed silently

`ControlServer`'s `status` reply aggregates 20+ sub-status objects
(wifi/battery/power/config/ota/imu/calibration/indicators/scan_health/
findme/...) and has grown to **~5200 bytes** as the firmware gained
features. The ESP-NOW frame format allowed only `16 * 240 = 3840` bytes.

`EspNowFragmenter::fragment()` returns 0 for anything larger, and
`EspNowPairing::serviceCommand()` then set `responseFragCount_ = 0` and
sent **nothing at all, with no error and no log** -- the device printed
`control_command_finished ok=true` while the Hub never received a single
fragment. That made a deterministic size limit look exactly like an
intermittent RF/transport fault, which is why earlier rounds of
airtime/contention fixes never resolved it. Smaller replies
(`memory_status`, `scan_health`) always worked, which is what finally
isolated it.

- Fragment budget raised to **32 fragments (7680 bytes)**, the hard ceiling
  for the wire format (`EspNowReassembler`'s arrival bitmask is a
  `uint32_t`). Only the *control* path grew: data and OTA paths stay pinned
  to the original 16-fragment budget, so the OTA chunk size is byte-for-byte
  unchanged and the RAM cost stays confined to where it was needed.
- Fixed a latent undefined behaviour this exposed: the reassembler computed
  `(1u << fragCount_) - 1u`, which for `fragCount_ == 32` is a shift equal
  to the width of `uint32_t`. On ESP32 it wraps to `1u << 0`, so a
  32-fragment frame would be reported complete on its *first* fragment.
  Covered by a new native regression test that fails without the fix.
- A response that still doesn't fit now returns an explicit
  `response_too_large` error (with the byte counts) instead of going silent.

### 2. Radio-level send failures silently destroyed multi-fragment responses

With the size limit lifted, a newly-added `esp_now_register_send_cb()` (this
project had never registered one) revealed that **1-2 of the 22 response
fragments failed at the radio level per attempt**. `esp_now_send()`
returning `ESP_OK` only means the packet was queued -- delivery failure is
reported asynchronously, so it was invisible. Since the reassembler needs
every fragment, a single loss destroyed the entire response.

Response fragments are now sent **stop-and-wait**: each one waits for its
send callback and is retransmitted (bounded retries, with a callback
timeout) if the radio reports failure. This is what took `status` from
intermittent to 8/8 reliable.
